## 2. 기술 아키텍처 및 코드 품질

### 강점

- 데이터와 화면 로직이 정적 JSON 및 브라우저 계산에 분리되어 있어 별도 서버·DB의 고정비와 운영 부담이 낮다. 이용량이 지금 수준에서 크게 늘어도 읽기 트래픽은 CDN/정적 호스팅에 맡길 수 있다.
- `useScheduleData`는 일정 기본값과 증분 업데이트를 ID 기준으로 병합하고, 증분 자료의 같은 ID는 필드 병합으로 덮어쓴다. 힌트·추천영상·브리핑 등 부가 JSON의 파싱 오류를 각각 처리하고, 일정 엔진·개발 중 validator를 공용으로 호출한다.
- 예측 엔진은 확정 데이터, 버전별 힌트, 기본 주기의 우선순위를 두고, 변칙 주기·목표일·방송 날짜·방송 생략·후반 픽업 주기를 표현한다. 이미 확정된 연속 버전을 따라 미래 기준점을 옮기며 최대 홉 수와 방문 버전 집합으로 무한 반복을 막는다. 간트 표시 기간도 차기 패치 및 수동 종료일을 반영한다.
- `validateSchedule`은 날짜 형식과 같은 날 대형 업데이트, 동일 게임 중복, 통상 요일·주기, 후반 일정, 공식 방송, 오프라인 행사 등을 진단한다. `npm build` 앞에 검증을 두어 오류가 나면 빌드 종료하도록 연결한 것은 좋은 운영 게이트다. 날짜 변경 감지 후 캘린더를 자동 생성하는 Vite 플러그인도 편의성이 높다.
- Python 캘린더 생성기를 Node 브릿지가 실행하는 방식은 이미 있는 Pillow 기반 도구를 활용한다. `calendar_meta.json`과 월별 이미지 아카이브가 UI 표시와 다운로드 이름에 연결되어 있다.

### 기술 부채와 실패 모드

1. **선택 JSON의 네트워크 실패가 앱 전체 로딩 실패로 번질 수 있다.** 일곱 fetch가 `Promise.all`에 묶여 있어 부가 JSON 하나라도 네트워크 자체가 reject되면 필수 일정이 정상이어도 catch로 가며, 현재 코드는 부가 JSON의 HTTP 오류·파싱 오류는 허용해도 네트워크 reject는 격리하지 않는다. 필수/선택 리소스를 분리하거나 각 응답을 `allSettled`로 수집하면 핵심 일정의 가용성이 좋아진다.
2. **JSON 스키마를 빌드 단계에서 완전하게 검증하지 않는다.** validator는 도메인 오류를 꽤 깊게 검사하지만, 모든 레코드의 필수 필드, enum, 고유 ID, `end_date`의 실제 달력 유효성 등을 정식 스키마로 검증하는 계층은 확인되지 않았다. 정규식은 `2026-02-31`을 거르지 않는다. 일정 JSON의 출처·갱신 시각 및 필드 정의를 JSON Schema/Zod 등으로 명시할 것을 권한다.
3. **날짜 계산이 브라우저 로컬 시간대에 기대고 있다.** `parseDate`는 `new Date(y,m-1,d)`를 쓰고 일수 차이는 밀리초를 86,400,000으로 나눠 내림한다. 일광절약시간제 지역에서 자정 간 차이는 23/25시간일 수 있어 하루 차이가 잘못 계산될 여지가 있다. ISO 날짜를 UTC 일수 정수로 계산하거나 날짜 전용 라이브러리로 규칙을 고정해야 한다. 운영자 로컬이 한국이어도 해외 이용자 브라우저에서 처리된다.
4. **고정 설정값과 데이터 설정값의 중복이 있다.** 엔진은 `gamesConfig`와 JSON의 `games_config`를 둘 다 참조한다. 우선순위가 명확하지만 두 값이 어긋나면 개발자에게 원인을 찾기 어려운 비대칭 동작이 생긴다. 단일 설정 원천 및 빌드 시 불일치 검증이 낫다.
5. **현재 예측 결과에는 이용자가 날짜의 근거와 갱신 시점을 빠르게 판단할 메타데이터가 부족하다.** 확정/예상 뱃지는 있지만 예측 산식·마지막 확인일·출처 링크·변동 이력·정확도 통계는 별개로 노출되지 않는다. 버전별로 `prediction_basis`, `as_of`, `source`, `confidence_band`를 담고 실제 확정일과 비교해 예측 오차를 기록하면 신뢰도와 운영 효율을 함께 높일 수 있다.
6. **캘린더 자동 생성은 로컬 Python 설치 및 Pillow에 의존한다.** `generateCalendar.js`가 PATH에서 Python 실행 파일을 찾아 호출한다. 개발 PC에서는 편리하지만 CI의 Python 버전·패키지 미설치, 경로 차이, generator 실패 시 stale 이미지가 남는 상황을 별도 관리해야 한다. build 단계의 검증 통과 뒤 이미지 생성 실패가 경고로만 처리될 수 있으므로, 최신 이미지 생성이 배포 필수인지 정책을 분리하고 CI 환경을 고정할 필요가 있다.
7. **회귀 테스트가 확인되지 않는다.** 요청 범위의 정적 검토에서 단위/통합 테스트 스위트가 확인되지 않았다. 주요 경계 시나리오(윤년·시간대, 연속 확정 버전, 힌트 대상일, 버전 점프, 같은 날짜 충돌, 누락 JSON)를 자동화하는 테스트가 없으면 수동 일정 데이터 변경이 예측 엔진을 조용히 깨뜨릴 수 있다.

### 확장성 판단

읽기 중심이며 데이터 크기가 작고, 게시 시 갱신을 허용하는 도구에는 정적 호스팅이 적절하다. 서버리스라서 “트래픽 무제한”은 기술적으로 보장되지 않는다. 호스팅 사업자의 전송량·요청 제한, 원본 이미지 크기와 캐시, JSON 버전 캐시 정책은 여전히 상한이 있다. 로그인, 개인 알림, 사용자별 저장 동기화, 다중 운영자 편집, 승인 워크플로가 제품 요구가 될 때 API나 DB를 추가하면 된다. 그 전까지는 정적 JSON을 유지하고 생성·검증·게시 자동화에 투자하는 편이 비용 대비 합리적이다.

## 3. UX / UI 및 제품 사용성

- `GanttView`는 오늘 기준 과거 30일과 미래 90일을 날짜 축으로 보여주고, 게임명 열과 날짜 축을 sticky 처리한다. 데스크톱에서 게임 간 패치·방송 겹침을 비교하기 좋다. 날짜 축 폭이 큰 구조는 좁은 화면에 그대로 축소할 수 없으므로, 모바일에서 너비를 줄이고 별도 리스트 뷰를 제공하는 선택은 적절하다.
- 리스트는 날짜순 이벤트 카드, 오늘 마커, 게임·버전·확정 상태, 상세 클릭과 Enter/Space 키 조작을 제공한다. 키보드 활성화를 구현한 점은 긍정적이다. 다만 카드 `div role=button`은 버튼 요소보다 의미·포커스 기본 동작이 취약하고, 클릭 카드의 접근성 이름·포커스 표시·스크린리더 읽기 순서를 계속 점검해야 한다.
- 달력 모달은 현재 이미지, `alt` 설명, 확대 보기, 파일명 지정 다운로드 및 GA4 추적을 갖춰 저장·공유 니즈에 직접 맞는다. 2048 정사각 캘린더는 모바일에서 한눈에 읽기보다 확대/다운로드 활용을 염두에 둔 선택으로 보인다. 이 기능의 실제 다운로드 성공 여부는 현재 `download_calendar_image` 클릭 이벤트만으로 측정할 수 없다. 브라우저 다운로드 시작과 파일 완료는 웹페이지에서 같은 의미가 아니므로 이벤트 이름과 분석 해석을 “버튼 클릭”에 한정해야 한다.
- 목적 달성 시간 10-30초라는 설계 목표는 짧은 체류시간을 성공으로 볼 근거를 제공하지만, 실제 과업 성공률을 입증하는 지표는 아니다. “필요 일정 발견”, 검색/필터 이후 이탈, 다운로드 성공, 일정 오정보 제보, 코호트 재방문을 측정해야 목적형 UX의 성과를 판정할 수 있다.

**우선 UX 개선:** 확정/예상 구분 대비를 색상 외 아이콘·문구로 보완, 모달의 키보드 포커스 이동/복귀 확인, 모바일 터치 타깃과 긴 제목 줄바꿈 점검, 예측 근거와 마지막 검토일 노출, 일정 날짜 복사/캘린더 등록(ICS) 수요 검증.

- 같은 이벤트 보고서의 `toggle_game_filter`는 776회 / 154명, `click_schedule_event`는 413회 / 109명, `open_modal`은 590회 / 154명이다. 이는 실제로 다수 사용자가 일정을 필터링하고 세부 카드를 열어 본다는 제품 사용 신호다.
- `view_calendar` 76회 / 38명, `download_calendar_image` 35회 / 21명으로 관측됐다. 35/38=92%를 다운로드 CVR로 보는 것은 잘못이다. 같은 기간 같은 코호트에서 달력 보기 후 다운로드까지의 사용자 경로가 제공되지 않았고, 달력 보기 이벤트가 분모에 적합한 퍼널인지도 검증되지 않았다. 분명히 말할 수 있는 것은 다운로드 이벤트가 21명에게 기록됐다는 점이다.
- `click_recommended_video` 11회 / 5명, `click_youtube_channel` 3회 / 3명이다. 측정된 직접 이동은 존재하나 현재 숫자만으로 사이트-채널 유입 플라이휠이 강하다고 할 수 없다. 추천 영상 클릭의 목적지·동일 사용자 이후 YouTube 행동 연결도 확인되지 않는다.
- 별도 2026-08-09부터 09-05까지 28일 요약은 MAU 505, 일평균 DAU 24.6, returning 사용자 비율 41.9%다. 기간 정의가 다른 요약이며, 8월 25일부터 9월 21일 자료의 재방문 비율로 대체하면 안 된다. 운영자 프롬프트에 기재된 55-66% 재방문은 현재 열람한 최신 기간 요약에서 독립적으로 검증되지 않았다.

### 증가 원인과 채널 디커플링

운영 보고서는 9월 초 캘린더 기능 배포와 9월 8일 유튜브 커뮤니티 안내(1.6만 노출)를 피크와 연결한다. 날짜가 근접하므로 설득력 있는 가설이지만, 두 변화가 동시에 일어난 데다 GA4 캠페인 링크, referral/source-medium, 실험군 및 기능 배포 전후 동질 기간 비교가 없다. 따라서 “안내 게시와 제품 개선이 유입에 기여했을 가능성”으로 표현해야 하고 인과효과라고 단정하면 안 된다.

채널 성과와 별개로 사용자들이 일정 필터·상세 카드·달력 기능을 사용했다는 점은 제품의 독립 효용을 지지한다. 다만 이 자료만으로 채널에서 완전히 디커플링했다고 결론 낼 수는 없다. 트래픽 출처가 없기 때문이다. 다음부터 유튜브/커뮤니티별 UTM을 분리하고, GA4 `session source/medium`, 신규·재방문, 랜딩 페이지, 코호트 유지율을 기능 출시일·콘텐츠 게시일과 함께 추적해야 한다.

### 측정 개선

1. 달력 퍼널을 `calendar_open` → `calendar_download_click` → 가능하면 다운로드 응답 성공으로 분리하고, 주간 방문자 등 명확한 분모에서 사용자 단위 전환율을 계산한다.
2. YouTube 커뮤니티·영상 설명·고정 댓글에 채널별 UTM을 붙여 세션 소스와 첫 방문 이후 재방문을 구분한다.
3. 사용자 식별 또는 동의 범위에서 7/28일 재방문 코호트와 세션 참여 시간을 보고한다. `first_visit`와 `returning_users` 집계를 혼동하지 않는다.
4. 핵심 과업 이벤트(필터 적용 후 일정 상세 열기, 일정 링크 클릭, 다운로드)를 일관된 파라미터 스키마로 수집한다. `target_url` 전체 문자열 전송은 쿼리 파라미터에 개인정보가 들어갈 여지가 있으므로 허용 도메인·경로만 보내고 query/hash를 제거한다.

## 5. 취미 채널과 개발 프로젝트의 상호 가치

이 프로젝트의 성과는 사업 자산의 크기보다 개인 필요에서 시작한 기능을 작동하는 웹 서비스로 완성하고, 실제 이용자의 사용과 반응을 관찰하며 개발 경험을 쌓은 데서 찾아야 한다. 게임 일정 영상과 사이트는 주제가 맞닿아 있어 채널 게시물·댓글로 사이트를 안내하고, 사이트 안에서 영상 큐와 채널 링크를 노출하는 상호 보완 구조를 만든다. 유입에 운영자의 지속적인 직접 안내가 기여했으므로 “완전히 자생하는 플라이휠”이라고 부르기보다는, 취미 채널의 꾸준한 소개와 제품의 유틸리티가 함께 작동하는 교차 홍보 경로라고 보는 편이 정확하다.

사이트에는 가벼운 자발적 후원 링크가 있지만 실제 후원은 발생하지 않았고, 후원·광고·스폰서십을 통한 수익화 계획도 없다. 따라서 MAU나 이벤트 수를 매출 잠재력으로 환산하거나 제휴 영업 로드맵을 제안하는 것은 프로젝트의 목표와 맞지 않는다. 후원 기능의 유무는 운영을 지지하고 싶은 이용자를 위한 선택지 정도로 해석하면 된다.

커피·영화관 등 서브컬처 제휴는 향후 개인 취미의 범위에서 재미있는 협업 가능성으로 남겨둘 수 있으나, 현재 성장 목표나 필수 로드맵은 아니다. 핵심 화면과 데이터 신뢰를 유지하고 운영자에게 즐거운 개발 경험을 주는 것이 우선이다.

- 채널의 댓글·게시물 안내와 사이트 안의 영상 추천을 적절히 이어 주되, 직접 홍보가 기여한 유입임을 성장 평가에 투명하게 남긴다.
- 운영자 부재에 대비해 입력 체크리스트, 롤백 절차, 데이터 백업 및 최소 2인 검수 흐름을 마련한다.

## 결론

AEIKA Archive는 개인적으로 필요했던 일정 기능을 바이브 코딩으로 구현하고, 이를 공개 사이트로 확장해 실제 이용자가 사용하는 단계까지 가져간 취미 개발 프로젝트다. 입문자가 React 앱, 데이터 파이프라인, 예측 로직, 검증 게이트, 배포형 이미지 생성, GA4를 한 흐름으로 경험했다는 점이 개발자 관점의 핵심 성과다. DAU·MAU와 기능 이벤트는 사용자가 실제로 찾아왔음을 보여주지만, 댓글·커뮤니티 게시물 등 운영자의 꾸준한 직접 안내가 유입의 일부를 만들었다. 이 사실은 성과를 깎는 꼼수가 아니라 초기 개인 프로젝트가 사용자를 만나는 현실적인 배포·홍보 활동이며, 유기적 확산과 구분해 설명할 요소다.

다음 단계는 사업화가 아니라 프로젝트를 만든 사람의 학습 목표와 개인적 효용을 이어 가는 일이다. 날짜 경계 테스트, 선택 데이터 로딩 격리, 스키마 검증, 예측 오차 기록 같은 개선은 더 견고한 소프트웨어를 만드는 실전 학습 과제다. 필요와 흥미가 이어지는 범위에서 기능을 다듬고, 채널과 사이트가 서로를 소개하며 함께 성장하는 경험 자체를 성공 기준으로 삼는 것이 이 프로젝트에 맞다.
